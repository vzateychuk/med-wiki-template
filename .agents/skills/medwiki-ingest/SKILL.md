# Ingest в med-wiki

Шаблон страницы — по таблице в начале `AGENTS.md`. Других шаблонов не используй, структуру не выдумывай.

Имена **новых** файлов — только по `.agents/skills/medwiki-file-naming/SKILL.md` (программа `naming.py`). Тип документа и маппинг — там. Здесь имена не придумывай. Файлы, которые уже лежат в `raw/`, этого не касается — см. «Файл уже в `raw/docs/`».

Уточнения у пользователя (неясная рекомендация, сомнительная цифра, сомнительный slug метрики) — копи в список и задай **одним блоком в конце** шага 10. В середине процесса не спрашивай по одной, кроме шага 0 (нет даты → предложи дату и одним вопросом подтверди).

| Вход | Раздел |
| --- | --- |
| Скан, фото, PDF меддокумента | «Меддокумент», с шага 0 |
| Готовый текст меддокумента | «Меддокумент», шаг 1 пропусти |
| Статья, транскрипт видео или лекции | «Статья» |
| «Пересобери метрику X» / «почини динамику X» | «Метрики», маршрут K |
| Много файлов сразу | «Пакет» |

## Меддокумент

Перед шагом 0: это **документ для ingest**, а не заметка (§S)? Критерий в `AGENTS.md` (граница I/S): готовый текст = I, если ≥2 признака (дата; врач/клиника/бланк; структура заключения или таблица анализов; скан/«из выписки»). Пересказ своими словами без этого → не этот навык, маршрут **S**. Сомнение — один вопрос пользователю.

### Файл уже в `raw/docs/`

Если пользователь указал файл, который уже лежит в `raw/docs/`, он и есть источник. Имя не проверяй, с `naming.py` не сверяй, не переименовывай, не копируй и не пересоздавай; шаги 0–2 пропусти. Дату события бери из текста документа, а не из имени. Если даты в тексте нет — спроси её, как в шаге 0.

**Загружался ли файл:** открой реестр `wiki/sources/_index.md` (нет файла — создай по шаблону `index.md`, раздел «Реестр»). Строка с этим файлом есть — документ уже загружен: повторно не обрабатывай, скажи об этом пользователю. Строки нет — загружай с шага 3, в ссылках на источник используй фактический путь файла. Других проверок (поиск по `wiki/`, хэш, сравнение имён) не делай. Первую строку файла не дописывай: это правка существующего файла.

| Шаг | Действие |
| --- | --- |
| 0 | **Только для нового файла вне `raw/`. Только имена.** По навыку имён: извлеки дату и тип, вызови `naming.py` для `raw/docs` (с `--check-exists raw/docs`) и `raw/images`. Имя занято (код 4) — документ, вероятно, уже загружен: не создавай новое имя, спроси пользователя (подробности — навык имён). Файлы ещё не записывай. Даты в тексте нет — **предложи** наиболее правдоподобную дату и одним вопросом попроси подтвердить или поправить (без даты имя не построить). |
| 1 | Сохрани оригинал в `raw/images/` под именем из шага 0 (страницы `-p1`, `-p2`, …). |
| 2 | Распознай текст, сохрани в `raw/docs/` под именем из шага 0. Первой строкой — ссылка на оригинал(ы). Текст не исправляй и не дополняй. Нечитаемое — `[НЕЧИТАЕМО]`. Сомнительные даты, дозы, значения показателей — в список уточнений к шагу 10. |
| 3 | Тип смысла: консультация, анализы, исследование, выписка (для выбора шагов ниже; имя файла уже задано типом из навыка имён). |
| 4 | Каждый диагноз: создай или обнови `wiki/diagnoses/<slug>.md`. Обнови **Статус** — как сейчас по этому документу. В **Историю** — одна строка: дата, короткий факт, ссылка на `raw/docs/`. Новое сверху. Тот же факт той же даты не дублируй. Заключение целиком не копируй. Новый диагноз со статусом `active` или `monitoring` — добавь ссылку в строку нужного направления в **Активных направлениях** `wiki/profile/me.md`; подходящей строки нет — добавь строку. Диагноз стал `resolved` — убери его из направлений. Раздела «Открытые вопросы» на странице диагноза нет и не создавай. **Связанные метрики** и **теги** — см. «Шаг 4 — связи диагноз ↔ метрика» и «Шаг 4 — теги диагноза». |
| 5 | **Метрики — схема А (авто со всей панели).** См. раздел «Метрики». На панели анализов пропуск показателя с именем и значением — ошибка, не норма. **Связанные диагнозы** на странице метрики — см. «Шаг 4 — связи диагноз ↔ метрика». |
| 6 | Назначения и отмены — `wiki/profile/medications.md`. Нет активных препаратов — как сказано в шаблоне `medications.md`. Историю приёма не переноси. |
| 7 | Новые аллергии — `wiki/profile/allergies.md`. Факторы риска, рост, вес, состав тела — `wiki/profile/me.md`; новое значение заменяет старое в строке, старое остаётся в `raw/docs/`. |
| 8 | **Открытые действия** — только файл `wiki/profile/open-actions.md`. Синтез, не копирование строк документа. |
| 9 | Каталоги `wiki/_index.md` и `wiki/*/_index.md`: ссылка и одна строка. В каталоге диагнозов — статус из шапки страницы. Каталог метрик обновляй вместе с шагом 5. **Реестр:** последним действием шага добавь строку документа в `wiki/sources/_index.md` (ссылка на `/raw/docs/<имя>`, дата загрузки); строка уже есть — не дублируй. Для пакета — после каждого документа. |
| 10 | Отчёт в чат: какие сущности обновлены и что это меняет в картине; противоречия с уже записанным; **один блок** «нужно уточнить» (если список не пуст). Без пересказа документа. Затем §H из `AGENTS.md` по изменениям. |

### Шаг 4 — связи диагноз ↔ метрика

Раздел **«Связанные метрики»** на странице диагноза — запись о том, какие показатели врач назначил для контроля этого состояния. По нему маршруты P и H (`AGENTS.md`) выбирают показатели. Обратная сторона — раздел **«Связанные диагнозы»** на странице метрики.

**Откуда брать связь (только факт из документа, без клинических догадок):**

| Источник в документе | Пример | Куда |
| --- | --- | --- |
| «Назначенные обследования» — назван показатель | «Липидограмма + АСТ, АЛТ» | метрики этих показателей |
| «Контроль …» / «Оценка …» в названии обследования | «Контроль функции щитовидной железы» → ТТГ | ТТГ |
| «Мониторинг» на странице диагноза, если там назван показатель | — | метрика этого показателя |
| Панель анализов без диагнозов | см. таблицу ниже | диагноз той же темы, **если он уже есть в wiki** |

**Панель анализов без диагнозов.** В панели часто нет диагнозов, но есть метаданные шапки и примечания. Связь с диагнозом выводится из них:

| Где в панели | Пример | Куда |
| --- | --- | --- |
| Заголовок панели | «Маркеры костного метаболизма (паратгормон, остеокальцин, PINP)» | остеопения, остеопороз — если такой диагноз есть в wiki |
| «Органы:» в шапке | «костная система, паращитовидные железы» | остеопения |
| «Система:» в шапке | «иммунная», «репродуктивная» | аллергический ринит, вульвовагинит |
| Примечания панели | «Назначено эндокринологом для оценки функции надпочечников» | диагноз по надпочечникам, если он есть в wiki |
| Название файла панели | `…_lab-panel-gynecology.md` | гинекологические диагнозы |

Связь ставится, только если в wiki **есть** подходящий диагноз и панель явно указывает на его тему. Нет подходящего диагноза — не создавай его и не выдумывай связь: показатель остаётся без «Связанных диагнозов», это не ошибка.

**Правила:**
- Связь **симметрична**: заполнил одну сторону — заполни и вторую.
- **Дополняй, а не перезаписывай.** Новый документ добавляет строки; удаляй строку, только если источник, который её дал, прямо отменяет назначение.
- Валидный показатель — есть страница в `wiki/metrics/` (шаг 5). Нет страницы, а показатель нужен — сначала создай её, потом связь.
- **Не выдумывай.** Нет в документе показателя для этого диагноза — раздел пуст; это не ошибка. Пустой раздел при наличии назначенных обследований — ошибка. Нет подходящего диагноза в wiki — не создавай его ради связи.
- Общие анализы «для профилактики», не привязанные в документе к диагнозу, не пиши.
- Инструментальные исследования (УЗИ, рентген, денситометрия) — не метрики: в «Связанные метрики» не пиши, они в «Мониторинг».
- Диагноз `resolved`: связи оставь, из «Активных направлений» в `me.md` убери.

### Шаг 4 — теги диагноза

`tags` в шапке диагноза обязательны и не пусты (`AGENTS.md`, Execution Rule 2): 1–3 тега латиницей, нижний регистр — тема (орган, система) и область.

Примеры: `endocrine`, `thyroid`, `bone`, `cardiology`, `lipids`, `gastro`, `liver`, `gynecology`, `allergy`, `ent`, `ortho`, `neurology`, `hematology`, `uro`, `dermatology`. Список открытый: нужного нет — введи короткий английский тег по теме; перед этим посмотри теги уже существующих диагнозов и используй совпадающий, а не синоним.

Диагноз `resolved`: теги оставь и добавь тег `resolved`.

### Страницы, созданные до этих правил

При ingest или lint перечитай документ-источник из «Истории» и заполни пустые «Связанные метрики», пустые `tags`, пустые «Связанные диагнозы». Источник показателей не назначал — оставь пустым. Существующие строки не перезаписывай — дополняй.

### Шаг 8 — правила синтеза `open-actions.md`

Пиши только дела пользователя: визит, обследование, «Начать приём …» со ссылкой на `/wiki/profile/medications.md`.  
Не пиши: вопросы врачу, дозы и схему препаратов (схема — в `medications.md`), размытые ярлыки без глагола.

Этот подраздел — единственный источник правил составления таблицы дел; при расхождении с проверкой базы (`medwiki-lint`) действует он.

**Лимит длины:**
- колонка **Действие** — не длиннее **~120 символов**; глагол + объект; подготовка/место — одна короткая фраза в той же ячейке («натощак», «после УЗИ»), без абзаца.

**Фильтр попадания в таблицу.** Число строк не ограничено: в таблице столько дел, сколько проходит фильтр.
- В таблицу идёт разовый конкретный шаг (визит, обследование, «Начать приём …»), который врач назначил или рекомендовал и который ещё не выполнен. Подходит: «Сдать…», «Записаться…», «Начать приём…». Не подходит: «рекомендуется контроль», «при необходимости».
- Всё остальное — регулярное, «контроль через N месяцев» без конкретного шага, необязательное, низкоприоритетное — в **Мониторинг** страницы диагноза, не в open-actions.
- Дело по явной просьбе пользователя добавляется в обход фильтра.
- **Запись в Мониторинг:** со ссылкой на документ-источник (`/raw/docs/…`). Если пользователь закрыл дело как неактуальное — с пометкой «закрыто пользователем».
- **Возврат из Мониторинга в таблицу** — только если вышел более новый документ **того же профиля** (п. 5), который подтверждает, что дело нужно сделать, или по прямой просьбе пользователя. Дело без пометки «закрыто пользователем» при проверке базы можно предложить вернуть, если оно проходит фильтр. Дело с пометкой «закрыто пользователем» при проверке базы не предлагается.

1. **Группируй** — связанные обследования (один визит / одна проба / один день) = одна строка.
2. **Задача** — глагол + объект («Сдать…», «Записаться…», «Сделать УЗИ…», «Начать приём…»).
3. **Срок** — `YYYY-MM-DD` или «не указан»; только следующий конкретный шаг. Регулярное / ежегодно → **Мониторинг** диагноза.
4. **Размытое** («Инсулин») — не добавляй; если ясно из документа — сформулируй сам, иначе в уточнения шага 10.
5. **Суперсессия и дедуп** — новый документ **того же профиля** заменяет в open-actions строки, источником которых был **более старый** документ того же профиля; затем добавь синтез из нового. Один смысл = одна строка (оставь более конкретную / с ясным сроком).

   **Профиль документа** — не «все `consultation` подряд». Это пара:

   | Часть | Откуда взять |
   | --- | --- |
   | Тип | Суффикс типа в имени файла: `consultation`, `lab-panel`, `discharge`, `ultrasound`, … |
   | Специализация | 1) disambiguator в имени после типа (`…_consultation-allergist.md`, `…_consultation-lor.md` → `allergist` / `lor`); 2) если в имени нет — специальность/отделение из тела («аллерголог», «ЛОР», «эндокринолог»); 3) нет ни там ни там — специализация пустая |

   Примеры: `consultation/allergist` и `consultation/lor` — **разные** профили (новая консультация аллерголога не стирает дела от ЛОРа). Два файла `consultation/allergist` — один профиль (новый заменяет старый). Два `lab-panel` без специализации — один профиль `lab-panel`. Выписка `discharge` не суперсессит консультации.

6. **Возраст строки (два разных случая):**
   - **Календарно просрочено** — в колонке **Срок** стоит дата, она уже в прошлом, и нет более нового документа, который подтверждает, что дело ещё нужно → кандидат на удаление (это не про «не указан»).
   - **Без срока, устарело** — **Срок** = «не указан». Возраст — по дате в имени файла-источника. Если источнику **≥ 12 месяцев** и нет более нового подтверждающего документа **того же профиля** (см. п. 5) → кандидат на удаление. Не копи строку вечно.
   - **Удаление — только после подтверждения пользователя.** Кандидатов не удаляй молча: перечисли в блоке «нужно уточнить» (шаг 10) или, при проверке базы, списком. Ответ «удалить» — строка удаляется; «оставить» — спроси новый срок, не назвал — поставь дату через неделю от сегодняшней.
   - Замена строк более свежим документом того же профиля (п. 5) идёт автоматически, без вопросов.
7. **Таблица** — одна; строки идут по сроку: ближайшие сверху, «не указан» в конце; при равном сроке порядок не важен. **Причина** — ссылка на диагноз; **Источник** — `/raw/docs/…`.

По типу документа:

- Панель анализов — шаг 5 обязателен для **каждого** показателя с именем и значением; шаг 4, только если в заключении есть диагнозы.
- Консультация — шаги 4, 6, 8; шаг 5, если в тексте есть числовые или качественные результаты анализов (не дозы лекарств).
- Исследование — шаги 4 и 8; шаг 5, если есть измеримое или качественное значение показателя.
- Выписка — шаг 4 для каждого состояния, шаги 6 и 8; шаг 5 для показателей в тексте. Период уже покрыт более полной выпиской — переноси только то, чего в wiki нет.

Запрещено: `wiki/visits/`, протокол приёма, пересказ анализа, копия тела документа, страница wiki на каждый документ, раздел «Открытые вопросы» на диагнозе или жалобе.

## Метрики

**Схема А:** при загрузке панели анализов каждый показатель с **названием и значением** создаёт или обновляет страницу в `wiki/metrics/` и строку в `wiki/metrics/_index.md`. Пользователю не нужно говорить «веди ТТГ». Полный текст панели по-прежнему в `raw/docs/`.

Каталог — `wiki/metrics/_index.md` (колонки: slug, название, страница). Страница — по шаблону `metric.md` (`value_kind`: `numeric` | `qualitative` | `panel-item`).

### Имя → slug

```bash
python .agents/skills/medwiki-file-naming/resolve_metric_slug.py "Тиреотропный гормон (ТТГ)"
# → {"slug":"tsh", ...}
```

Словарь: `schema/metric-synonyms.yaml`. Резолвер — **только точное** совпадение имени (см. навык имён). Нет в словаре — сопоставь с `_index.md` по смыслу. **Не** подклеивай по подстроке и **не** плоди второй slug молча.

**Сомнение о slug (нужна страница сразу):** выбери один провизорный slug (резолвер или `slugify` имени из бланка), запиши страницу и строку динамики **сейчас**, в блок уточнений шага 10 добавь: исходное имя, выбранный slug, вопрос «тот же показатель, что X, или отдельный?». После ответа пользователя: тот же — допиши синоним в yaml и при необходимости слей/переименуй; другой — оставь как есть или раздели по ответу. Не жди согласия, чтобы закончить ingest панели.

Разный биоматериал при одинаковом слове в бланке — разные slug (`wbc` кровь / `wbc-urine` моча / `wbc-vagina` мазок). Ratio, % и абсолют — всегда разные страницы.

### Динамика

Дата документа, значение (число **или** качественный текст как в документе), референс, статус, ссылка на `raw/docs/`. Одна строка на пару (дата + исходное название показателя). Та же дата и значение — пропусти; та же дата, другое значение при том же названии — в уточнения шага 10. Два разных названия из одной панели на один slug — ошибка склейки: раздели slug, не пиши обе строки на одну страницу. `status` в шапке — по последней строке.

Статус из текста: норма → `normal`; повышен / высокая / выше → `elevated`; понижен / низкий / ниже → `low`; пограничный / незначительно → `borderline`. Не сопоставилось — `borderline` и пометка в уточнениях.

### Качественное и аллергопанели

- ПЦР / мазок / «обнаружено–не обнаружено» → `value_kind: qualitative`.
- Каждый аллерген / компонент панели с своим значением → отдельная метрика `panel-item` (через резолвер или новый slug).
- Клинически значимые аллергены **дополнительно** — строка в `wiki/profile/allergies.md`.
- Целиком панель остаётся в `raw/docs/` для цитаты «всего листа».
- Не создавай метрику из фразы-интерпретации без собственного значения и из доз лекарств.

### Маршрут K (не для первичного заведения с панели)

«Пересобери метрику X» / «почини динамику X» / устаревшее «добавь X в ключевые»: пересобери страницу и строки динамики из **всех** уже загруженных `raw/docs/`, где показатель встречается под любым синонимом того же slug. Используй, если динамика битая, неполная или после расширения словаря синонимов.

## Статья

1. Имя в `raw/articles/` — только через `naming.py` по навыку имён. Сохрани в `raw/articles/`.
2. `wiki/references/<slug>.md` по шаблону `reference.md`: источник, сжатые тезисы, явные связи с диагнозами пользователя.
3. Каталоги. В чат — короткое резюме.

Тезис статьи — не личный медицинский факт. Без связи с `wiki/diagnoses/` это справочный слой.

## Пакет

**Один** файл или готовый текст — пилот и список «до начала» не нужны: сразу шаги 0–10.

**Пакет** (два и больше документов / папка):

1. Пилот 3–5 файлов (по возможности по одному документу каждого типа: полная выписка, новая панель, новая консультация). **Кратко перечисли** состав пилота в том же сообщении и **сразу начинай** обработку — не жди отдельного «ок». Остановись только если пользователь явно сказал подождать или вычеркнул файлы.
2. Lint по `.agents/skills/medwiki-lint/SKILL.md`.
3. Остальные пакетами по 10–15, lint после каждого.

Список «что осталось» в пакете — файлы `raw/docs/` без строки в реестре `wiki/sources/_index.md`.
